# Grafana Alerting architecture and rule ownership

## When to load
Creating or changing a rule in Grafana.

## Procedure
Determine whether rule is Grafana-managed, datasource-managed or generated by SLO tooling; inspect version/edition and supported datasources. Map rule folder/group, evaluation engine, rule UID, labels/annotations, contact points, notification policies and alertmanager instance. Use backend-supported queries with explicit scope/windows; dashboard variables and visual transformations are not generally available to alert evaluation. Choose multidimensional rules where one semantic condition applies per bounded scope; control instance cardinality. Follow existing provisioning/source-of-truth workflow; preview condition and routes in staging, verify write permission and rollback before authorized deployment.

## Required evidence and acceptance
Rule preview plus actual backend evaluation, expected labels/instances, notification policy test, state and managed asset revision evidence.

## Guardrails
Do not create one rule per ephemeral pod, mix ownership or assume rule import validates notification delivery.
