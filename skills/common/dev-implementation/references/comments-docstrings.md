# Comments and docstrings

## Use when
Public contracts, non-obvious invariants or tradeoffs.

## Avoid when
Narrating obvious syntax or explaining why requested work was skipped.

## Implementation
Follow the language documentation convention; document inputs, results, units, exceptions, side effects and invariants as relevant. Comments explain why, not what. Link issue for real deferred work; remove stale TODOs and dead code.

## Verification and review
Documentation matches behavior; incomplete requirements are reported in delivery notes.
